The custom viewer text editor now has an explicit per-viewport IME composition lifecycle instead of a frame-number suppression window: an active composition is owned by the edit session's layer/session identity, and a target switch or editor end turns it into a tombstone. An empty pre-edit is the observed end of the visible composition, but its terminal commit/delete can arrive in a later event, so the owner stays associated with the cleared composition; if the target changes before that terminal event, the tombstone rejects it instead of applying it to the replacement. A lone non-empty old pre-edit keeps the tombstone across arbitrary idle frames. A rejected terminal commit consumes the tombstone immediately, so a new pre-edit later in the same raw input batch starts a composition for the current target. A rejected empty pre-edit or delete-surrounding keeps the tombstone through the rest of that batch so its paired old commit is rejected too, and is consumed at batch end when no commit follows. A composition started after that terminal boundary is accepted, so the tombstone never becomes a permanent lock. egui::ImeEvent payloads still carry no context generation, and the inspected egui-winit 0.37 source ignores Ime::Enabled/Ime::Disabled and implements should_interrupt_composition by toggling set_ime_allowed without an observable reset acknowledgement. The fallback therefore drops the first ambiguous composition after an unobserved platform reset rather than claiming provenance it cannot prove; a producer-side event epoch would be needed to close that residual, and this is not claimed as tested on a real platform IME here. Two real-app headless regressions in crates/ui-egui/tests/it/ui_text_edit.rs cover the observed-empty-preedit pending commit and a new pre-edit after a stale terminal commit in the same raw batch; this revision adds them but does not claim they were rerun here. The later bounded same-owner interruption repair (2026-10-24) tracks the expected caret and selection separately from that immutable layer/session owner. A live or terminal-pending composition is invalidated before application pointer/selection changes can accept an old IME mutation, including keys before a later IME event in the same raw batch and control-client selection changes before a pass. Accepted IME mutations update the expected selection so the IME deletion's own caret shift does not reject its paired commit. The existing terminal rules still permit a fresh preedit after a rejected terminal commit, and a direct commit with no active composition remains valid even after a pointer change in the same batch. Five new real-app regressions cover15 scenarios with both deletion forms, pointer and keyboard interruption, terminal-pending/external selection, undo preservation, fresh composition and direct commits. These new source bytes and tests await parent-managed formatting, focused/full gates and fresh independent review; no new test, native-IME or final dependency-graph acceptance is claimed here.

Every future push or new pull request still needs a fresh, explicit human approval of the exact commit range and its validation; this document is not publication evidence.

Scope: storytold/effectcraft only (this checkout). Shared work in storytold/craft-libs (PR 199 and the CL-2 capture helper), the suite egui fork and the suite winit fork are dependencies with their own plans; this document records what EffectCraft needs from them, not what they should do. 2. What actually changes in egui 0.37 that affects EffectCraft

This section is limited to changes visible in the pinned sources. It corrects two assumptions that must not enter the plan:

  • App::logic / App::ui and Context::run_ui are not new in 0.37. They already exist in 0.36.2 (egui-0.36.2/crates/eframe/src/epi.rs:167,182; egui-0.36.2/crates/egui/src/context.rs:794), and EffectCraft already uses them (crates/ui-egui/src/lib.rs:1852-1935, apps/effectcraft/src/main.rs:426-456, apps/effectcraft-web/src/app.rs:88-122). The migration is not a wholesale update-to-ui rewrite.
  • Context::run_logic is not a substitute for a pass. It does not interpret time or events; run_logic only refreshes viewport state (egui-0.37.0/crates/egui/src/context.rs:1190-1218). Calling it cannot initialise fonts or consume input.

2.3 Behaviour changes that compilation will not catch

These are the app-specific risks, each with a source anchor and a planned assertion.

  1. default_fonts is no longer a default feature of egui/epaint. eframe still enables it by default, but EffectCraft disables eframe defaults and re-enables only default_fonts, wgpu, accesskit, links, wayland, x11 (crates/ui-egui/Cargo.toml:25, apps/effectcraft/Cargo.toml:18). The app relies on FontDefinitions::default() at theme.rs:334; the feature must stay explicitly enabled on the egui dependency, not only through eframe, so cargo check -p effectcraft-ui-egui and test builds are deterministic. (#8583; egui-0.37.0/crates/egui/Cargo.toml:40-46.)
  2. The bundled emoji fonts are no longer in FontDefinitions::default(). In 0.36.2 the default definitions include NotoEmoji-Regular and emoji-icon-font unconditionally (egui-0.36.2/crates/epaint/src/text/fonts.rs:490-580). In 0.37 they are behind monochrome_emoji_fonts, and the default only adds the small egui-icons font (egui-0.37.0/crates/epaint/src/text/font_definitions.rs:105-180). EffectCraft's own chrome is affected. A read-only cmap audit of the fonts actually bundled by this app and by egui found:
    • ✔ U+2714 (menu check gutter, menus.rs:2176) is in only NotoEmoji and emoji-icon-font;
    • ▣ U+25A3 (Media Browser folder, media_panels.rs:198; Essential Graphics media row, essential.rs:247) is in Hack and emoji-icon-font, but Hack is not in the app's Proportional family (theme.rs:339-347 only prepends Inter and appends JetBrains Mono), so only the emoji font covers it;
    • ✓ U+2713 (checked label text, widgets.rs:485) is in Inter/JetBrains Mono and unaffected. Without monochrome_emoji_fonts these two become tofu, and kittest's default MissingGlyphPolicy::Panic turns that into test failures.
  3. Clipboard support became an eframe feature. 0.36.2's eframe always enabled egui-winit/clipboard (egui-0.36.2/crates/eframe/Cargo.toml:152). 0.37 gates it behind clipboard (egui-0.37.0/crates/eframe/Cargo.toml:142-144), which is in eframe's default set but not enabled by EffectCraft's default-features = false manifests. Without it, cut/copy/paste to the OS clipboard silently degrade to an in-app simulated clipboard (egui-winit-0.37.0/Cargo.toml:44-46), breaking Edit ▸ Copy/Paste, text-field paste and menus.rs:1867-1906 which maps clipboard events back to command keys.
  4. Screenshots are callback based (#8489; data/screenshot_callback.rs, ViewportCommand::Screenshot(ScreenshotCallback), Context::request_screenshot). The current correlation by UserData token through Event::Screenshot is impossible (lib.rs:1530-1580, control.rs:439-444). See §5.7.
  5. WidgetType and ID APIs are deprecated, and the CI clippy gate is -D warnings (xtask/src/main.rs:412). This is 626 mechanical Id::new occurrences (616 lines) plus the 19 source role edits and one more in ui_agent_audit.rs (see §5.2/§5.3).
  6. AccessKit roles/names are enforced by kittest 0.37. HarnessBuilder defaults check_accessibility: true and Harness::run panics on visible input widgets without a name (egui_kittest-0.37.0/src/builder.rs:50-51, src/accessibility.rs:9-45). is_input covers Button, CheckBox, ColorWell, ComboBox, Slider, SpinButton, Splitter, Tab, TextInput, TreeItem, … (egui-0.37.0/crates/egui/src/accessibility.rs:9-60). Many of the app's stock TextEdit, DragValue and Slider fields are currently unnamed (39 TextEdit::singleline/multiline constructors out of 44 TextEdit:: references, and 51 DragValue/Slider constructors), and custom ui.interact widgets have no WidgetInfo at all.
  7. Missing glyphs panic in kittest 0.37 (#8601; MissingGlyphPolicy::Panic is the harness default, builder.rs:50). Tests that deliberately render uninstalled scripts must opt out with HarnessBuilder::allow_missing_glyphs(); two are already known: tests/ui_effect_names.rs:35 (the builder inside harness() at line 20, used by the zh-hans tests at 68, 81, 107 and 127, including 高斯模糊) and tests/ui_presets_folder.rs:40 (ja). Fontconfig on this planning host lists no faces at all, so those tests would panic rather than draw tofu until a CJK face is installed or the opt-out is used.
  8. Ui::id → Ui::scope_id, UiBuilder::id → scope_id, Panel constructors take impl AsIdSalt. EffectCraft does not use SidePanel/TopBottomPanel, and uses CentralPanel::default() only (dock_ui.rs:475, prefs_live.rs:207), so no panel-order rewrite is needed. The root Ui is already the app surface (lib.rs:1905-1935, lib.rs:1614-1723). Never call Context::root_ui from a panel or a test closure: it panics while the root Ui is borrowed (context.rs:1005-1055).
  9. Style defaults changed (roomier buttons, larger corner radii; #8617, #8445). EffectCraft pins item_spacing, button_padding, interact_size.y, menu_margin, scroll style and all widget corner radii from tokens (theme.rs:510-530, theme.rs:474-495), so the visible impact should be small, but atom-based Button/ComboBox layout can still move geometry. This is a geometry/pixel test target, not an assumption.
  10. Menus/popups and text editing changed (#7802, #7624, #8572, #8548, #8763, #8628). EffectCraft builds its own menu bar and keyboard navigation (menus.rs:2025-2050, menu_keys.rs), with MenuConfig style overrides. Regression tests must cover hover-switch, arrows, submenu opening, outside-click close, and a button acting on a focused TextEdit's selection (the #8763 case). Container tooltips now also show when their children are hovered (#7909); check tooltip presence/absence on the app's large custom interact rects (viewer, timeline, dock) instead of assuming the 0.36 behaviour.

3. Fork, winit and craft-libs integration decisions

3.1 What EffectCraft actually needs from the suite fork

4. Root-Ui, lifecycle and multi-pass semantics

4.1 Current split (already on 0.36.2, must be preserved and completed)

Today EffectcraftApp::logic does GPU-failure application, language/theme/font install, FPS, control drain, screenshot scheduling/collection (lib.rs:1870-1903), while ui calls frame() which does polls, playback, events, autosave, prefs, window title, close guard and the whole paint (lib.rs:1905-1935, lib.rs:1614-1723).

Verified integration facts (candidate source, same call sites as upstream 0.37):

  • eframe runs logic and ui inside one Context::run_ui closure for every full pass (eframe-0.37.0/src/native/epi_integration.rs:349-364; web app_runner.rs:289-292). A full pass can run more than once per frame when Context::request_discard is used.
  • While the root window is minimized/occluded, native eframe runs Context::run_logic with App::logic only (epi_integration.rs:384-425), unless a Screenshot or RequestPaintWhileHidden action is pending, in which case it runs a full UI pass with current input and paint (wgpu_integration.rs:680-740).
  • prepare_raw_input calls raw_input_hook before both paths (epi_integration.rs:414-428). update_logic_only then stores the hook-mutated raw input in pending_raw_input for the next full pass (epi_integration.rs:400). Therefore synthetic events fed during a logic-only call are retained, not lost, and are applied exactly once by the next full pass.
  • Native eframe throttles repaints of an invisible/minimized window to at least 100 ms (eframe-0.37.0/src/native/run.rs:27,376-383), so a hidden gesture or capture takes a few throttled full passes; the app's deadlines must allow for that and must not infer failure from the first 100 ms.
  • ViewportInfo::visible() derives from minimized/occluded, not from a paint request. It stays Some(false) during a forced hidden UI pass, so visibility cannot distinguish "logic only" from "forced hidden paint".
  • run_logic refreshes only raw.viewports and raw.focused (egui-0.37.0/crates/egui/src/context.rs:1190-1218); it leaves InputState::time, events and pointer state at the previous pass's values. eframe sets RawInput::time in prepare_raw_input, but run_logic does not copy it into InputState.
  • Context::request_screenshot sends a viewport command, which requests a repaint, and a pending screenshot is a "wants paint" action even when hidden. The callback itself does not request a repaint when the pixels arrive.

Consequences, all pre-existing in 0.36.2:

  • With the window minimized/occluded, job polling, playback advance, audio pumping, auto-save ticks, engine-event draining, the unsaved-close guard and the window-title update do not run on ordinary logic-only ticks.
  • A discarded pass re-runs the run_ui closure, so logic runs again for the same frame. Grid requests a discard on first show (egui-0.37.0/crates/egui/src/grid.rs:468); EffectCraft has 18 Grid::new sites across dialogs/settings/forms.
  • The control channel's AfterInput replies are completed in logic as soon as synthetic is empty, which is before the pass applies the last synthetic event (lib.rs:1893-1901, lib.rs:1921-1930). While hidden, an event can also have been fed into retained raw input with no pass yet applied.

  • Focus comes from the fresh viewport copy with a visible-pass fallback:

  • Synthetic input is not gated on visibility, but is gated on an unapplied event. raw_input_hook runs once per eframe prepare (frame or logic call), not per egui UI pass, and calls self.feed_synthetic(raw_input) then pointer_wrap::prepare_input(...). In a logic-only call eframe retains the mutated raw input (pending_raw_input) and calls the hook again on the next call; in a forced hidden full pass it is applied immediately. Gating on visible() == Some(false) would skip feeding in both cases and leave the gesture (and its reply) pending forever. feed_synthetic drains one pointer event per call (lib.rs:578-591), so repeated logic-only updates before the forced full pass (eframe's overdue-RedrawRequested path and its 100 ms invisible-window throttle) would append press, move and release to the same retained input and collapse a gesture into one pass. The hook must therefore set a guard when it moves a synthetic event into raw input and skip feeding while that guard is set; the guard is cleared when a known UI pass has applied that step once, even if layout is later discarded; record that application separately from screenshot settling/accepted-frame counters. RawInput events are consumed on the first pass and are not replayed in later passes. Never clear the guard in tick; never wait for the event to reappear in an accepted pass. The next step is fed only on a subsequent host input preparation. No event is discarded. §8.3 tests repeated logic-only ticks with a drag and a click.
  • raw_input_hook performs no reply, no clock read and no side effect other than pointer-wrap state, the synthetic-pending guard and merge-key closing. pointer_wrap::prepare_input returning "gesture ended" clears session.history.merge_key; doing that during a logic-only call is safe because the events are retained and the same reset is idempotent.
  • Replies for AfterInput are completed only at the end of a non-discarded draw pass (after the pass, check !ui.ctx().will_discard()) that ran after the last synthetic event was fed, and never in tick. A hidden request therefore replies only after the forced pass applied it, and a pass that egui throws away cannot produce an early success reply.
  • If a control request needs a UI pass (synthetic input, a panel-window change, or a caller that explicitly wants fresh ui.inspect/ui.elements data), tick sends RequestPaintWhileHidden.
  • control::handle is called from tick with now passed in (a signature change, not a wrapper): replace its ctx.input(|i| i.time) at control.rs:428 with now, and inspect's windowFocused at control.rs:562 with ctx.input(|i| i.viewport().focused). ui.inspect and ui.elements keep last-painted semantics.

4.4 Multi-pass and idempotence

A discarded pass re-runs tick and draw with the same raw input (events are taken by the first pass). Rules:

  • tick effects are idempotent for a replayed pass: polls drain queues; auto-save checks a timestamp; advance_playback computes the target frame from the plan and the monotonic now rather than incrementing, so a replay with a slightly later now does not double-count Playback::frame_shown (lib.rs:230-246); screenshot scheduling advances only when now passes a settle deadline, never once per pass (the old frame counter must not be replayed); job-waiter completion is keyed by the pending job, not by pass count.
  • One-shot side effects in draw must rely on egui's per-pass input (Response::clicked, drag_stopped) and command merge keys, not on layout-pass counts. High-risk paths are viewer drags (viewer.rs:1674-1874), timeline drags (timeline.rs:1500-1700), painting strokes (layer_panel.rs:350-360) and form toggles inside Grids.
  • Add a forced-discard regression test (§8.3) that proves one undo step and one command effect across a real two-pass frame.

A switch before that terminal event therefore still rejects it rather than applying it to the replacement. A non-empty old pre-edit is treated as a continuing update of that old composition and keeps the tombstone across arbitrary idle frames. A rejected terminal commit is the composition boundary and consumes the tombstone immediately, so a new pre-edit later in the same raw input batch is accepted for the current target. A rejected empty pre-edit or delete-surrounding is only tentatively terminal: it keeps the tombstone through the rest of the batch so a paired old commit is rejected too, and is consumed at batch end when no commit follows. Tests must separate the late pre-edit from its commit/delete by at least three idle frames, exercise an observed empty pre-edit followed by a target switch and a delayed old commit, verify a new pre-edit after a rejected terminal commit in the same batch commits to the new target, verify a genuinely new composition after the consumed terminal batch, and verify that no permanent lock remains. 5.7 Screenshots (control channel, kittest, hidden windows)

Replace token-via-input-event correlation with the shared CL-2 completion slot (§3.3). Do not add an unbounded or app-local result channel: the slot is owned by the app request record, and the callback holds only a weak reference to it.

struct PendingShot {
    token: u64,
    path: Option<String>,
    crop: Option<[f32; 4]>,          // logical points, as the control protocol already takes
    reply: Sender<Value>,
    deadline: f64,                   // app clock
    admitted: (egui::Rect, f32, u64), // screen rect + ppp + geometry epoch at acceptance
    issued: Option<(egui::Rect, f32, u64)>, // target-UI rect + ppp + geometry epoch at issuance
    slot: Arc<capture::CompletionSlot>, // CL-2F helper type (API frozen)
    reserved_bytes: usize,
}
  • Admission. Use the shared default policy: at most 4 outstanding requests, 128 MiB per image and 256 MiB aggregate reserved in-flight/completed bytes. Stricter app caps are allowed, but never looser. Estimate the target surface with checked width * height * 4 from the known UI geometry, reject over-budget requests before issuing a capture with an actionable reply, and revalidate the reservation at issuance. A post-callback size check alone does not bound peak capture memory; the reservation does.
  • Issue. ctx.request_screenshot(callback) sends a viewport command that itself forces a repaint, and a pending screenshot makes a hidden window take a full UI+paint pass. A screenshot that is merely queued and not yet issued, and settling deadlines, must have tick/logic send RequestPaintWhileHidden so the UI reaches issuance; do not add a second wants-paint request once the screenshot command has been issued. At issuance record the target-UI logical content/screen rect, ppp and a geometry epoch. That issued geometry + epoch, not callback metadata, is bound to the image: the callback carries only pixels.
  • Completion. The app owns the strong slot and the owner-specific waker; the callback holds only a weak reference, stores the image unless canceled/completed, takes the wake handle, drops the slot lock, then requests the owning viewport's repaint. The callback does not wake itself and must not strongly capture a Context or the app; that would create a cycle with the viewport's queued command. collect_screenshots drains completed slots in tick and encodes/writes/replies outside the callback.
  • Geometry/scale binding. With an unchanged geometry epoch, derive the pixel scale from the returned image dimensions against the issued rect and verify aspect/rounding; the returned image may be smaller when E2 surface fitting applies. Any intervening resize/DPI/zoom/surface epoch change between admission, issuance and save cancels and retries the request — even if the geometry later changes back before the save. Never crop with the admission-time, current or any other ppp that disagrees with the issued epoch. Store admitted/issued/captured values and record mismatches; an explicit error is correct when a retry cannot complete inside the deadline.
  • Cancel/timeout/drop. Removing the request record (timeout, close, app drop, caller drop) marks its slot canceled under the lock; a late callback finds no live slot or a canceled one and drops the image without a second reply or file write. Release the reserved bytes on every exit path (completion, timeout, cancellation) and assert retained bytes return to zero after drain.
  • save_screenshot takes the actual scale/geometry instead of &egui::Context (control.rs:570-606), so it can run in tick.
  • issue_screenshots (lib.rs:1530-1558) uses the tick's now and a settle deadline, not a per-pass frame counter; collect_screenshots (lib.rs:1560-1580) becomes the slot drain.
  • Remove the "occluded/minimized" refusal at lib.rs:1490-1498 for the native wgpu path only after the platform run shows the screenshot request really produces a frame. The refusal exists because 0.36 never painted a hidden window; 0.37 makes a pending screenshot a wants-paint action (wgpu_integration.rs:680-690, egui-winit/src/lib.rs:2116-2128). Keep the timeout error and add ui.focus as the fallback. Record Windows/macOS/Linux results separately. Do not claim hidden-window screenshots on a platform that was not tested. On web, eframe does not paint a hidden tab (logic-only passes have no clipped primitives), so ui.screenshot on web requires a visible tab; record that limitation.
